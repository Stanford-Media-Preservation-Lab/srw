# srw — Claude Code Context

Context for continuing development on this project. For usage/install docs see [README.md](README.md), [MANUAL.md](MANUAL.md), [INSTALL_UBUNTU.md](INSTALL_UBUNTU.md).

## What this is

`srw` (SMPL RAWcooked Workflow, package `srw`) is a batch preservation transcoding tool for the Stanford Media Preservation Lab (SMPL), developed collaboratively with Claude over several months beginning January 2026. It takes folders of DPX image sequences (with optional WAV audio) from film scanning and packages them into lossless FFv1/Matroska (MKV) files for an OAIS digital repository, via a resumable ten-step workflow (inventory, checksum verification, MediaConch validation, MD5 manifest, RAWcooked transcode, metadata tagging, review derivative, MediaInfo technical metadata, final hashing), preceded by a Step 0 pre-flight check. Michael is the primary developer/maintainer.

Ubuntu-only — its dependencies (`rawcooked`, `mediaconch`, `mkvtoolnix`) don't have a supported macOS path, unlike this lab's other pipx tools ([vdg](https://github.com/michaelangeletti/vdg)) which run cross-platform.

**Lab infrastructure:**
- Primary workstation: AMD Threadripper Pro 3955WX (16c/32t, Zen 2), 128 GB ECC DDR4-3200, ASUS WRX80 Pro, Ubuntu 24.04, multiple NVMe + RAID array.
- Secondary/main production workstation: Dell Precision 7920 tower, dual Intel Xeon Gold 5220R @ 2.20GHz (48 cores total across two sockets), 128 GB RAM, Ubuntu 24.04. ~25 TB storage: two 6 TB RAID volumes (RAID 1, RAID 2) plus two 4 TB NVMe drives. This is the machine actually doing production DPX work — 12 TB / hundreds of thousands of DPX files processed as of 2026-07-14 (using the original pre-packaging script, not yet `srw`).

**Real deployment pattern on the Xeon (this is what `srw batch` was built for):** DPX sequences are copied in batches to each RAID volume, typically three batch folders per RAID, each containing its own `Source`/`Documents`/`MediaConch`. All batches on RAID 1 process to MKV/derivatives on NVMe drive A; all batches on RAID 2 go to NVMe drive B. That's up to six simultaneous `srw run` jobs. Watching `htop`/system monitor during six-parallel runs showed low resource usage — but that doesn't rule out an I/O ceiling (RAWcooked is typically storage-bound, not CPU/RAM-bound); the actual per-machine limit hasn't been measured yet via `iostat`/`iotop` against the RAID/NVMe devices specifically. No hardcoded parallelism limit should be assumed or built into tooling until that's done empirically.

## Current state

At **v1.4.0**. The original script (developed iteratively as `smpl-rawcooked_v3_batch1.py` / `SMPL_RAWcooked_v3_6_260116_Ubuntu24_04.py`) was refactored into an installable `srw` package (`srw/cli.py`) to match this lab's other pipx tools, then extended with a batch orchestrator, batched MediaConch validation, and safer sidecar handling once real production use on the Xeon (above) surfaced each need in turn:

- **v1.0.0:** Hardcoded per-deployment config variables (`BASE_DIR`, `MKV_OUT_DIR`, `DOCS_DIR`, `MC_DIR`, `MC_POLICY`, `WAV_POLICY`) were replaced with CLI flags (`--source-dir`, `--output-dir`, `--docs-dir`, `--mediaconch-dir`, `--dpx-policy`, `--wav-policy`, `--attachment-size`) — deployment no longer requires editing the installed script. All nine workflow steps, the resume system, and log format are behaviorally unchanged from the original script.
- **v1.1.0:** Added `srw batch` (`srw/batch.py`), a subcommand that reads a TOML config of `{batch_dir, output_dir}` pairs and launches one `srw run` per entry in parallel (via `python -m srw run ...` subprocesses, no shared state with the parent process). This required restructuring the CLI into `srw run`/`srw batch` subcommands — the old bare `srw --output-dir ...` invocation is gone; it's `srw run --output-dir ...` now. Bumped `requires-python` to `>=3.11` to use stdlib `tomllib` for the TOML config (no new dependency) — safe since Ubuntu 24.04 ships 3.12 and this tool is Ubuntu-only anyway.
  - Batch job default naming derives from `batch_dir`'s parent + basename (e.g. `/mnt/raid1/batch1` → `raid1_batch1`), not basename alone — basename alone collides in exactly the real deployment pattern above, where `batch1`/`batch2`/`batch3` repeat identically across both RAID volumes.
  - Fixed a latent bug while wiring this up: `srw run` (formerly bare `main()`) never actually exited non-zero when a sequence failed midway — it printed the error and returned normally, so a shell script or subprocess caller couldn't detect failure from the exit code alone. `run_main` now returns 0/1 and `main()` calls `sys.exit()` on it. This matters more now than it used to, since `srw batch` depends entirely on each `srw run` subprocess's exit code to know whether that batch succeeded.
  - No concurrency cap is imposed by default (`--max-parallel` is opt-in) — see the deployment-pattern note above on why.
- **v1.2.0:** Steps 3–4 (MediaConch DPX/WAV validation) previously ran `mediaconch` once *per file*, via a `HOME=$(mktemp -d) mediaconch ...` shell string — three process spawns per file (bash, `mktemp`, `mediaconch`) and a leaked temp directory every time, never cleaned up. For a real 100,000-frame sequence that's 300,000 spawned processes. Michael raised this after building `srw batch`, prompted by watching his actual 12 TB/hundreds-of-thousands-of-files production run.
  - Verified empirically (not assumed) that MediaConch's CLI accepts a file list in one invocation and, with `-fc` (CSV format), returns clean per-file pass/fail — `mediaconch -p policy -fc file1 file2 ... fileN`. New `run_mediaconch()`/`validate_files_against_policy()` in `srw/cli.py` batch files (default `--mediaconch-batch-size` 2000, mainly to stay under `ARG_MAX` for a single exec) and use one CSV-format call per batch instead of one call per file.
  - The per-call `HOME` isolation (so MediaConch's own config/cache doesn't collide across concurrent `srw batch` jobs) is preserved, but now done via `tempfile.TemporaryDirectory()` directly in Python — no shell, no `mktemp` subprocess, and it's actually cleaned up afterward.
  - Halt-on-first-invalid-file semantics and full per-file policy-failure detail in the log are unchanged: `validate_files_against_policy()` is a generator, so later batches are never evaluated once the caller (`process_sequence`) stops at an invalid file; that one file gets a second, single-file `mediaconch` call (without `-fc`) to capture the same human-readable detail the log always had.
  - Deliberately did **not** reach for `concurrent.futures` here — batching alone cuts subprocess count by ~2000x for a 100k-frame sequence, and parallelizing chunks would complicate the halt-at-first-failure-in-original-order behavior for comparatively little additional gain. Revisit only if real timing on the Xeon shows batching alone isn't enough.
  - Verified against the real `mediaconch` binary (not just mocked unit tests) with synthetic DPX files and the actual lab policy — confirmed correct batching, correct halt/detail behavior, and confirmed the old leaked-temp-dir bug is gone.
- **v1.3.0:** Step 2 (Checksum Verification) previously *deleted* each source file's sidecar `.md5` immediately after verifying it. Michael pointed out the real risk: if `srw run` crashes or is halted anywhere in steps 3-9 and needs to be re-run from scratch, or if someone wants to re-verify the original transfer's integrity months later, there's nothing left to check against — the only record of "this is what the file's hash was supposed to be at ingest" is gone.
  - The deletion wasn't arbitrary, though — it's load-bearing for step 6. `rawcooked --all` embeds any stray files it finds in the source folder as MKV attachments (the same mechanism used to embed step 5's manifest); leaving thousands of per-file sidecars in place would mean RAWcooked tries to embed each one individually, likely breaking the "reversibility data must be the last attachment" constraint (see Known issues below).
  - Fix: step 2 now *relocates* each sidecar (via `shutil.move`, preserving the source folder's relative subfolder layout) to `{docs-dir}/{sequence_name}_source_md5_sidecars/` instead of deleting it — satisfies RAWcooked's constraint (source folder is still clean by step 6) while keeping a permanent baseline. Per user decision, these are kept indefinitely rather than auto-cleaned after a sequence fully succeeds — storage cost is negligible next to the actual DPX/MKV data, and no cleanup step means no new way to accidentally destroy the one surviving copy.
  - Made step 2 resumable at the per-file level, not just at the step level: if a prior attempt crashed mid-move (some sidecars already relocated, others not), re-running no longer misreports the already-relocated ones as "Missing MD5" — it checks the holding directory first and skips files already handled there. Verified with a synthetic sequence where 2 of 5 sidecars were pre-relocated to simulate a mid-step crash; resume correctly picked up the remaining 3 without touching the already-moved 2.
  - Not unit-tested (this logic lives inline in `process_sequence`, matching the existing convention of not testing that function directly) — verified manually with synthetic sequences covering both the normal full-pass case and the simulated mid-crash resume case.
- **v1.4.0:** Five enhancements requested together after the Xeon put real production runs through the tool, all landed in one pass:
  - **`--start-step`/`--end-step`** (both `1`–`10`, default `1`/`10`) let a run target a specific step range. `--start-step N` marks steps `1..N-1` complete in the log *without re-verifying them* (via `mark_step_complete`, so every step block's existing `is_step_complete()` check just skips them — no per-step special-casing needed) — for resuming when the process log itself was lost (drive failure) or the job progressed on a different machine and the user is otherwise certain those steps passed. `--end-step N` returns after step `N`'s block instead of continuing. Combined (e.g. `--start-step 3 --end-step 4`), they run an isolated step or range standalone — the motivating case was running MediaConch DPX/WAV validation on its own. **Skipping Step 2 this way does not relocate sidecar `.md5`s** (that's real file-moving side-effect work, not just a marker) — `srw` logs an explicit warning when `--start-step` > 2 for this reason; see [MANUAL.md](MANUAL.md#running-a-specific-step-range-start-step--end-step).
  - `check_dependencies()` is now range-aware (`STEP_DEPENDENCIES` dict + pure `tools_needed_for_range()` helper) — a narrow `--start-step`/`--end-step` range no longer demands tools it will never call (e.g. validating steps 3-4 alone doesn't require `rawcooked` on `PATH`). Picked up `ffmpeg` into this same check as a side effect of touching the function — it was previously never verified before Step 8 tried to shell out to it, an existing gap not worth leaving in place while restructuring this code anyway.
  - **New Step 9: MediaInfo Technical Metadata**, inserted before what was Step 9 (Final Hashes, now Step 10). Runs `mediainfo -f -i` against the finished MKV and writes the dump to `{docs-dir}/{sequence_name}_mediainfo.txt` for QC/database use, plus appends the same output to the process log. **This renumbers the log's step markers from 9 total to 10** — any sequence that already has a `>>> SUCCESS: Step 9 completed successfully.` marker from before this version will, under v1.4.0, have that marker misread as "MediaInfo done" rather than its actual old meaning ("Final Hashes done"), meaning mediainfo generation would be silently skipped for it while hashing (now step 10) reruns cleanly. Given production `srw` usage was minimal as of this change (see lab infrastructure note above — real production DPX work was still on the pre-packaging script), this was accepted rather than designing around it; flag it if any fully-completed-under-v1.3.0-or-earlier sequences turn out to exist and need their mediainfo dump generated separately (`mediainfo -f -i sequence.mkv > sequence_mediainfo.txt` by hand covers it).
  - RAWcooked's `.log` file (already output as a sidecar, not embedded — see Known issues below) now gets a short header prepended once Step 6 actually finishes encoding for the first time (`build_rawcooked_log_header()`/`prepend_rawcooked_log_header()`): lab name + `RAWcooked processing completed YY/MM/DD, HH:MM AM/PM`. Guarded by checking `is_step_complete("Step 6")` *before* calling `run_step_verbose` so the header is written exactly once, not re-prepended every time a resumed run re-scans the log for bypassed-prompt warnings (that scan itself runs unconditionally on every pass through this code, unchanged from before).
  - Step 1's inventory summary line now switches from MB to GB once the sequence total reaches 1 GiB (`format_total_size()`) — a real 28,114-frame sequence reported as "1050315.68 MB" prompted this; per-file sizes in the CSV are unchanged (still MB).
  - **New Step 0: Pre-flight Check** (`preflight_check()`), runs before Step 1 unless `--skip-preflight` is set. Deliberately scoped down from the full "does this script need to understand each film's components" idea floated alongside the request — implemented as a fast, mostly-informational report rather than a rules engine: hard-halts only on conditions that otherwise fail expensively late (missing `{sequence}.xml`, currently only caught at Step 7 after Step 6's RAWcooked transcode already ran; missing MediaConch policy file, currently only caught when Step 3/4 invokes `mediaconch` against a nonexistent path; insufficient disk space on `--output-dir`, added right after this landed once Michael flagged it as the check he was most surprised wasn't already there — see below). Audio Y/N, a best-effort DPX frame-numbering gap scan (`detect_dpx_frame_gaps()` — last digit run in each filename, reports integers missing from the min–max range; not foolproof for unusual naming), and sidecar `.md5` coverage are logged as warnings only, since Step 2 already halts with full per-file detail on a genuinely missing sidecar. Revisit the broader "per-film component awareness" idea only if this scoped version proves insufficient in practice.
    - **Disk space check** (`has_sufficient_disk_space()`, `--disk-space-margin`): required free space on `--output-dir` is total source (DPX+WAV) size times a margin, checked via `shutil.disk_usage()`. First cut of this used a flat `1.1` (assume ~1:1, i.e. essentially no compression) for every sequence; Michael pointed out this is needlessly pessimistic in practice — a clean B&W scan can land well under 50% of its DPX size with FFv1, while a grainy color negative might barely compress at all, so no single fixed ratio fits both, and always assuming the worst case risks a false-positive halt on exactly the large batches he's actually been running fine on his 4TB NVMes.
      - Revised to be self-calibrating (`estimate_disk_space_margin()`): Step 1 now also writes a machine-readable `>>> INVENTORY_TOTAL_BYTES: N` marker to the process log (`INVENTORY_TOTAL_BYTES_MARKER`, written with `print_to_screen=False` since it's not meant for a human watching the terminal). Before a new sequence's disk check runs, `srw` scans every other `*_process.log` in the same `--docs-dir`, keeps only sequences that reached `>>> SUCCESS: Step 10 completed successfully.` (i.e. a verified, fully-hashed MKV actually exists), pairs each one's recorded source-byte total with its actual finished `.mkv` size (`os.path.getsize`) to get a real compression ratio, and uses the **worst** (least-compressed) ratio seen so far — plus a smaller pad (`DISK_SPACE_HISTORICAL_PAD`, 1.05, vs. the flat default's built-in 1.1) since it's backing a real measurement rather than a total guess.
      - `DEFAULT_DISK_SPACE_MARGIN` (`1.1`) is now scoped specifically to the one case where there's no real data yet: the first sequence ever processed in a fresh `--docs-dir`. Every sequence after that in the same deployment uses the historical estimate instead, so the check gets less conservative as it learns the actual footage's behavior — exactly the "no hardcoded parallelism limits, measure empirically" pattern this lab already prefers elsewhere in `srw` (see [[srw-lab-infrastructure]]/`--max-parallel`), just applied to compression ratio instead of concurrency.
      - `Config.disk_space_margin` changed from a plain `float` default to `Optional[float] = None`; `None` means "estimate," and an explicit `--disk-space-margin` value always overrides estimation entirely (skips the historical scan). `srw.batch`'s per-job TOML override follows the same `None`-means-auto convention.
      - If `shutil.disk_usage()` itself fails (e.g. an exotic filesystem), this logs a warning and continues rather than halting — the check is a safety net, not something that should block a run entirely if it can't be answered.
  - `tests/test_srw.py` gained coverage for all of the above pure functions (`format_total_size`, `detect_dpx_frame_gaps`, `build_rawcooked_log_header`/`prepend_rawcooked_log_header`, `tools_needed_for_range`, `preflight_check` with synthetic fixtures). None of it touches `process_sequence` itself, matching the existing testing convention — validate the full step-range/pre-flight/mediainfo integration against a real or synthetic DPX sequence with the tools installed.
  - `srw.batch`'s `BatchJob`/TOML config gained matching optional `start_step`/`end_step`/`skip_preflight` fields, forwarded to each job's `srw run` subprocess exactly like the existing `attachment_size` override — so a batch config can, for example, re-run MediaConch validation only across several already-processed batches without redoing full runs.
- **Note on `--attachment-size`:** the source script hardcoded `-s 2000000` (2 MB) inline with no named variable; the design doc this repo was seeded from described a `RC_ATTACHMENT_MAX_SIZE = 5000000` variable and justified 5 MB against a real 44,420-frame sequence's ~2.6 MB manifest. This repo took the documented 5 MB figure as the default since it's the better-reasoned value and is now user-configurable either way — flag this to Michael if the 2 MB figure was actually intentional.
- MediaConch policy XML files (`DPX_SMPTE-CORE.xml`, `WAV_policy.xml`) were added directly on GitHub shortly after the initial commit — `MediaConch/` now ships the real lab policies, not just a `.gitkeep`.
- `tests/test_srw.py` covers the pure/testable `srw run` helpers (`verify_md5`, `is_step_complete`, `get_step_completion_timestamp`, `mark_step_complete`, config/argparse defaults, subcommand dispatch, and — with `subprocess.run` mocked — the MediaConch batching/parsing/laziness logic in `run_mediaconch`/`validate_files_against_policy`). `tests/test_batch.py` covers `load_batch_config()`'s parsing/validation/defaulting rules. Neither covers the actual subprocess-launching paths end-to-end (`process_sequence`, `_run_job`) — those shell out to real tools and were instead verified manually with synthetic DPX/batch fixtures during development; validate changes to them against a real (or synthetic) DPX sequence.

## Known issues and investigations

### RAWcooked segfault on Threadripper (return code -11)

**Symptom:** RAWcooked crashes with return code -11 (SIGSEGV) during the reversibility check phase, both during encoding and during reversal. Always at `Time=00:00:00 (0%)` — immediately at the start of the reversibility check, after the encode itself completes successfully. Passes on retry.

**Affected platform:** AMD Threadripper Pro 3955WX / ASUS WRX80 Pro / Ubuntu 24.04. **Not affected:** Dual Intel Xeon Gold 5220R / Ubuntu 24.04 — six parallel jobs completed without error on 661 GB of DPX sequences.

**Investigation results:**
- Thermals ruled out (Tctl max ~62°C under load); ECC errors ruled out (no MCE/EDAC in `dmesg`); BIOS current (v1801); RAM at native JEDEC 3200 MT/s.
- BIOS changes tested (IOMMU on, Core Performance Boost off, Memory Interleaving off) — no effect.
- Peak RAM per job ~1.7 GB — memory pressure ruled out.
- Valgrind: zero memory errors, but ~5000 warnings of repeated large-region `mmap`/`munmap` cycles on the same ~7.7 GB region, once per frame during the reversibility check. Valgrind serializes memory operations, which may be why the segfault doesn't reproduce under it.

**Hypothesis:** race condition or memory-mapping behavior in RAWcooked's reversibility check specific to Zen 2 / WRX80. **Workaround:** the resume system retries automatically; use the Xeon workstation for reversal work. A GitHub issue for MediaArea/RAWcooked is planned (Valgrind output + Xeon comparison data).

### RAWcooked reversibility data must be the last attachment
Confirmed by extracting and re-attaching reversibility data in last position, which restored reversal. Reported to MediaArea via GitHub. See [MANUAL.md](MANUAL.md#why-there-is-no-post-encode-attachment-step) for the full explanation of why this ruled out a post-encode `mkvpropedit --add-attachment` step.

## Development approach

- Iterative, incremental — preserve existing step behavior and log format with each change; the resume system depends on exact `>>> SUCCESS: Step N completed successfully.` marker text.
- Verbose terminal output is preferred: every step's subprocess output streams to both stdout and the process log.
- Log files include a consistent header banner identifying the lab; a `SCRIPT RESUMED` header is appended when re-run after interruption.
- Source and output directories should always be separate (`--source-dir` vs `--output-dir`) — mirrors a hard-learned convention from `vdg`, where sharing them caused resume logic to pick up derivative files as sources.
- Preserve all existing logic when adding features — changes should be surgical.

## Tools & ecosystem

- **RAWcooked** — lossless DPX-to-FFv1/MKV encoding with reversibility; version 25.12 in use at time of writing.
- **MediaConch** — policy-based validation of DPX and WAV files; validates actual file contents, not extensions.
- **mkvtoolnix** (`mkvpropedit`) — MKV metadata tagging; do not use `--add-attachment` post-encode (see Known issues).
- **FFmpeg** — H.264 review derivative generation.
- **tomllib** (stdlib, 3.11+) — parses `srw batch`'s TOML config; no third-party dependency added for this.
- **[vdg](https://github.com/michaelangeletti/vdg)** — sibling SMPL pipx tool (video derivative generation); `srw` was packaged to match its structure (pyproject.toml + console-script entry point, `bin/` thin wrapper, README/MANUAL/INSTALL split, CLAUDE.md context file).
